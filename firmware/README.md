# 바이브키 케어 기기 펌웨어 (VibeKey Care — Firmware)

Seeed Studio **XIAO ESP32-S3** 용 아두이노 스케치입니다.
버튼을 읽어, **깨지지 않았음을 보장하는 형태로** 폰에 전달하는 것이 이 펌웨어의 일입니다.

```
firmware/
├── vibekey_firmware/
│   ├── vibekey_firmware.ino   태스크 구성 · 핀 설정 · ISR (스케치 본체)
│   ├── vkp_frame.h            프레임 프로토콜(CRC16·재동기화)  ← 순수 C++, PC에서 테스트됨
│   ├── press_fsm.h            누름 판정 상태머신(디바운스·길게·떨림 가드) ← 순수 C++
│   ├── press_buffer.h         폰이 없는 동안 눌린 것을 담아 두는 링버퍼    ← 순수 C++
│   ├── pocket_guard.h         주머니·가방 안에서 눌린 것 걸러 내기         ← 순수 C++
│   ├── power_policy.h         언제·얼마나 잘지 정하는 규칙(워치독 상한 강제) ← 순수 C++
│   └── slot_store.h           버튼 매핑을 기기 플래시(NVS)에 담아 두기     ← 순수 C++
├── test/
│   ├── test_vkp.cpp           단위 테스트 (PC에서 실행)
│   └── run_tests.sh
└── README.md                  ← 이 문서
```

## 1. 왜 펌웨어를 다시 썼는가

개발 초기에 기기가 하는 일은 **GPIO를 읽어 `"True\n"` 을 뱉는 것**뿐이었습니다.
신호 해석, 손 떨림 방지(3초 디바운스), 실행 판단이 전부 안드로이드 쪽에 있었고,
기기는 사실상 전선이었습니다. 그래서 아래 세 가지 질문에 답할 수 없었습니다.

| 이 기기에 던져야 하는 질문 | 초기 시제품 | 완성된 작품 |
|---|---|---|
| 잡음 한 번이 그대로 실행되면? **신호 무결성은 누가 보장합니까?** | 아무도 | CRC16 + SEQ + ACK + 재전송 (`vkp_frame.h`) |
| 폰이 바쁘면 손 떨림 방지는? | 같이 무너짐 | 기기 상태머신이 독립적으로 판단 (`press_fsm.h`) |
| 버튼을 누르고 있으면 다른 버튼은? | 안 읽힘 (`while` 안에 갇힘) | 인터럽트라 세 개가 동시에 살아 있음 |
| 짧게/길게를 어떻게 구분합니까? | 구조적으로 불가능 | 700ms 판정 (`press_fsm.h`) |
| 전달이 실패한 걸 어떻게 압니까? | 알 수 없음 | 재전송 3회 후 실패 횟수를 세어 `STATS`로 보고 |
| 펌웨어가 멈추면? | 케이블을 뽑았다 꽂는 수밖에 | 태스크 워치독 5초 → 자동 재시작 |
| **눌렀는데 반응이 없었다면?** | 원인을 알 방법이 없음 | ISR이 놓친 접점을 세어 보고 (`놓친 버튼 입력 N회`) |
| **안 눌렀는데 실행되면?** (주머니·가방) | 그대로 실행됨 | 동시 눌림·오래 눌림·연달아 눌림을 기기가 판정해 차단 (`pocket_guard.h`) |
| 폰을 바꾸면 설정은? | 처음부터 다시 | 매핑을 기기 NVS에 저장 → 케이블만 꽂으면 되돌아옴 (`slot_store.h`) |
| 하루 종일 꽂아 두면 폰 배터리는? | 계속 240MHz 로 깨어 있음 | 조용하면 자고, 깰수록 길게 잠 · 연결 중에는 80MHz 로 감속 (`power_policy.h`) |
| 왜 재시작했는지 압니까? | 모름 | `esp_reset_reason()` 을 `HELLO` 에 실어 보고 |

기기에는 표시 장치가 없습니다(**버튼 3개 + USB가 전부**). 그래서 사용자에게 알리는 일은
폰이 맡되, **무엇을 알릴지는 기기가 보낸 프레임이 정합니다.** 몇 번 버튼인지·짧게인지
길게인지에 따라 폰이 서로 다른 진동 패턴을 울립니다(`Haptics.java`).

```
  1번 버튼  ·        2번 버튼  · ·      3번 버튼  —
  길게 누름 · —      성공      · ·      실패      — — —
```

부품을 하나도 안 늘리고 "화면을 보지 않아도 안다"를 만드는 방법입니다.
진동 장치는 이미 사용자 손에 있습니다 — **폰 안에**.

한 줄로: **MCU를 '전선'에서 '시스템의 신뢰 코어'로 올렸습니다.**

개발 초기의 스케치는 [`legacy/sketch_jul10a_v2.ino`](legacy/) 에 그대로 남겨 두었습니다(40줄).
무엇이 왜 달라졌는지 줄 단위로 비교할 수 있습니다.

## 2. 핀맵

XIAO ESP32-S3 의 D 표기와 실제 GPIO 번호입니다.

| 기능 | 보드 표기 | GPIO | 모드 | 비고 |
|---|---|---|---|---|
| 1번 버튼 | D0 | 1 | `INPUT_PULLUP` | 눌리면 GND로 떨어짐 (LOW = 눌림) |
| 2번 버튼 | D1 | 2 | `INPUT_PULLUP` | |
| 3번 버튼 | D2 | 3 | `INPUT_PULLUP` | ⚠️ 부팅 스트래핑 핀 — 아래 참고 |
| 지연 관측 | D10 | 9 | `OUTPUT` | 로직 애널라이저용 (`VK_LATENCY_PROBE`) |
| USB | — | 19/20 | 네이티브 USB CDC | 폰과의 통신 · 전원 |

**배선은 초기 시제품과 완전히 같습니다.** `firmware/legacy/sketch_jul10a_v2.ino` 가 쓰던 D0·D1·D2를
그대로 쓰기 때문에, 이미 만들어 둔 기기에 **펌웨어만 올리면 됩니다. 납땜은 한 번도 필요 없습니다.**
(D10 관측 핀은 지연을 잴 때만 쓰는 것이라 평소에는 아무것도 연결하지 않습니다.)

D3~D9 는 비어 있습니다. 나중에 표시 장치(LED 등)를 붙인다면 그쪽을 쓰면 됩니다.

**핀 선택에서 주의한 것**

- `D2`(GPIO3) — 부팅 스트래핑 핀(JTAG 소스 선택)입니다. 전원이 들어오는 순간 3번 버튼이
  눌려 있으면 스트래핑 값이 바뀝니다. 정상 부팅에는 영향이 없어 기존 배선을 유지했지만,
  **기판을 새로 뜬다면 `D8`(GPIO7)로 옮기는 편이 안전합니다.**
  `vibekey_firmware.ino` 의 `BUTTON_PINS` 배열에서 `3` 을 `7` 로 바꾸기만 하면 됩니다.
- `D6`(GPIO43) / `D7`(GPIO44) — UART0 TX/RX라서 쓰지 않았습니다.
- `D4`(GPIO5) / `D5`(GPIO6) — I²C 기본 핀. 확장(센서 추가)을 위해 비워 두었습니다.

## 3. 회로

### 3-1. 버튼 (3개 동일) — 이게 회로의 전부입니다

내부 풀업을 쓰므로 외부 저항이 필요 없습니다. 스위치 양단의 100nF는 접점 튐을
전기적으로 한 번 걸러 주는 용도이고, 나머지는 펌웨어 디바운스(25ms)가 처리합니다.

```
   3V3
    │
    ⌇  (ESP32-S3 내부 풀업 ~45kΩ)
    │
    ├──────────────► GPIO 1 / 2 / 3   (D0 / D1 / D2)
    │
   ─┴─  택트 스위치
    │        ┌──┤├──┐  100nF (선택)
   GND ──────┴──────┘
```

## 5. 소프트웨어 구성

### 5-1. 태스크

Wi-Fi를 쓰지 않으므로 모두 core 1에 올렸습니다(core 0은 USB·시스템).

| 태스크 | 우선순위 | 주기 | 스택 | 하는 일 |
|---|---|---|---|---|
| `inputTask` | 4 | 10ms | 3072B | ISR 큐를 비우고 누름 종류 확정 (`press_fsm.h`) · 워치독 신고 |
| `protoTask` | 3 | 5ms | 4096B | 프레임 송신 · ACK 대기 · 재전송 · 수신 해석 · 워치독 신고 |
| `loopTask` | 1 | 1s | (기본) | 잠들어 있음 — 실제 일은 위 둘이 합니다 |

**큐**

| 큐 | 깊이 | 항목 크기 | 생산자 → 소비자 |
|---|---|---|---|
| `edgeQueue` | 32 | 12B (`EdgeMsg`) | ISR → `inputTask` |
| `pressQueue` | 8 | 12B (`PressMsg`) | `inputTask` → `protoTask` |

**delay() 를 한 번도 쓰지 않습니다.** 초기 스케치는 버튼을 누르고 있는 동안 `while` 안에 갇혀
다른 버튼을 못 읽었습니다. 지금은 대기가 전부 `vTaskDelay` 라서, 한 태스크가 기다리는
동안에도 나머지가 계속 돕니다.

### 5-2. 누름 판정 (`press_fsm.h`)

```
        [대기] ──접점 LOW──► [눌림]
           ▲                   │
           │                   ├── 700ms 경과 ──► LONG 확정 (손 떼기 전에)
           │                   │                     │
           └──── 접점 HIGH ◄───┘                     ▼
                    │                            [대기(가드)]
                    ├── 직전 실행 후 1.2초 안 ──► 버림 (손 떨림)
                    └── 그 밖 ──────────────► SHORT 확정
```

- **디바운스 25ms** — 접점 튐 제거
- **길게 700ms** — 떼기 전에 확정합니다. 뗄 때까지 기다리면 "언제 떼야 하지?"를 모르는 어르신에게는 반응이 없는 것처럼 느껴집니다.
- **떨림 가드 1.2초** — 초기에 안드로이드가 떠안고 있던 3초 디바운스를 기기로 옮긴 것입니다. 중복 실행은 SEQ가 따로 막아 주므로 시간을 3초에서 1.2초로 줄여 반응을 빠르게 했습니다.
- **두 번 누름(DOUBLE)은 기본 꺼짐** — 켜면 "한 번 누름"을 확정하려고 매번 0.35초를 기다려야 해서 모든 실행이 그만큼 느려집니다. 기능 하나보다 즉각 반응이 중요하다고 판단했습니다. (`FsmConfig::doubleEnabled`)

### 5-3. 기기가 스스로를 감시하는 것

기기를 쓰는 분이 할 수 있는 일은 케이블을 뽑았다 꽂는 것뿐입니다. 그래서
"뭔가 이상하다"를 사람이 눈치채기 전에 기기가 먼저 알아야 합니다.

| 감시 | 방법 | 이상하면 |
|---|---|---|
| 태스크가 멈춤 | 태스크 워치독(TWDT) 5초, 두 태스크 모두 등록 | 패닉 → 자동 재시작 |
| 왜 재시작했나 | `esp_reset_reason()` 을 부팅 즉시 기록 | `HELLO` 에 실어 앱에 보고 |
| 버튼 입력을 놓침 | `xQueueSendFromISR` 실패 횟수 | `STATS` 의 `놓친 버튼 입력` |
| 메모리 누수 | 여유 힙 · 최저 힙 | `STATS` 에 KB 단위로 |
| 전압 강하 | 브라운아웃 감지(코어 기본 동작) | 재시작 후 원인 코드로 확인 |

**놓친 버튼 입력**이 특히 중요합니다. 이 기기에서 가장 나쁜 고장은 "눌렀는데 아무 일도
안 일어나는 것"인데, 그때 원인이 기기인지 폰인지 케이블인지 알 방법이 없었습니다.
이제 앱의 자가진단 화면이 `놓친 버튼 입력 0회 ✅` 를 보여 줍니다.

### 5-4. 주머니 오작동 차단 (`pocket_guard.h`)

이 기기의 가장 나쁜 고장은 두 가지입니다.

1. 눌렀는데 아무 일도 안 일어난다 → 오프라인 버퍼·재전송으로 막았습니다
2. **안 눌렀는데 뭔가 실행된다** → 여기서 막습니다

(2)가 더 나쁩니다. 사용자는 화면을 보지 않으므로 실행된 사실 자체를 모릅니다.
그런데 이 기기는 목에 걸거나 주머니에 넣고 다니는 물건이라, 옷감에 눌리는 일은
"있을 수 있는 일"이 아니라 **반드시 생기는 일**입니다.

부품을 늘리지 않고, 사람과 옷감이 누르는 방식이 다르다는 점을 씁니다.

| | 손가락 | 주머니 속 옷감 |
|---|---|---|
| 몇 개를 | 하나를 누른다 | 여러 개가 한꺼번에 눌린다 |
| 얼마나 오래 | 0.1~1초 | 한참 눌린 채로 있는다 |
| 몇 번을 | 한 번 누르고 결과를 기다린다 | 비비면서 여러 번 연달아 |

그래서 세 가지를 봅니다 — **동시 눌림**, **8초 넘게 눌림**, **3초 안에 5번 이상**.
하나라도 걸리면 그 누름을 버리고 1.5초 동안 모든 입력을 무시합니다(옷감은 한 번
스치면 계속 스치기 때문입니다). 조용해지면 스스로 풀립니다.

**"길게 누름"(0.7초 = AI 도우미)은 막지 않습니다.** 정상 동작을 막으면 그것 자체가 고장입니다.
테스트에 이 경우가 따로 들어 있습니다(`test_guard_allows_a_long_press_for_ai`).

판단을 폰이 아니라 기기가 하는 이유는 간단합니다. 걸러 내지 못한 신호는 이미 프레임이
되어 나갔고 폰은 그것을 정상 누름으로 받습니다. 폰에서 막으려면 폰이 깨어 있어야 하는데,
**주머니에 들어 있는 동안이 바로 폰이 잠들어 있는 시간**입니다.

걸러 낸 횟수는 `STATS2` 로 앱에 보고되어 자가진단 화면의 `주머니 오작동 막기` 에 뜹니다.
0이 아니어도 고장이 아니라 제대로 막고 있다는 뜻입니다.

### 5-5. 버튼 매핑을 기기가 들고 다닙니다 (`slot_store.h`)

"1번 버튼 = 카카오톡" 은 지금까지 폰에만 있었습니다. 그래서 폰을 바꾸거나 앱을 다시 깔면
어르신이 처음부터 다시 정하셔야 했습니다. 그 부담은 기기를 새로 받는 일과 다르지 않습니다.

이제 앱이 매핑을 정하면(직접 고르시든, AI가 정하든) 그 결과를 기기 플래시(NVS)에도 적습니다.
새 폰에 앱을 깔고 케이블만 꽂으면 기기가 먼저 알려 줍니다.

```
 기기                                      폰(안드로이드)
  ├─ HELLO(caps=CAP_SLOT_STORE) ──────────►│
  │                                         ├─ 폰에 정해 둔 것이 있나?
  │◄───────────────────── GET_MAP ──────────┤   없다 → "네가 들고 있는 걸 줘"
  ├─ MAP(slot=1, 0/3) ────────────────────►│
  ├─ MAP(slot=1, 1/3) ────────────────────►│
  ├─ MAP(slot=1, 2/3) ────────────────────►│   다 모이면 그대로 복원
  │                                         │
  │◄──────────────────── SET_MAP ───────────┤   있다 → "이걸 적어 둬" (다음 폰을 위해)
```

- **한쪽만 옳습니다** — 폰에 정해 둔 것이 있으면 폰이 옳고, 없으면 기기가 옳습니다.
  기기가 폰을 덮어쓰는 일은 없습니다. 어르신이 방금 바꾼 설정이 케이블을 꽂자마자
  옛날 것으로 되돌아가면, 왜 그런지 알 방법이 없기 때문입니다.
- **조각내어 보냅니다** — payload 한도가 16바이트인데 `com.samsung.android.dialer` 만 26바이트입니다.
  한도를 늘리면 앱 쪽 `FrameCodec` 과 규격이 어긋나므로, 한도는 그대로 두고 값을 13바이트씩 나눕니다.
- **절반은 저장하지 않습니다** — 조각이 하나라도 어긋나면 그 슬롯을 통째로 버립니다.
  절반만 저장된 매핑은 "눌러도 엉뚱한 앱이 열리는" 고장이 되는데, 화면을 안 보는 사용자에게
  그것이 가장 나쁜 결과입니다.
- **같은 값이면 플래시를 안 씁니다** — NVS 쓰기 수명을 아끼기 위해, 바뀐 슬롯만 적습니다.

### 5-6. 절전 — 하루 종일 꽂아 두는 물건이니까 (`power_policy.h`)

이 기기는 폰에서 전원을 얻는 유선 액세서리다. 목에 걸고 하루 종일 꽂아 두는 물건이라
아무 일도 안 하는 동안 폰 배터리를 먹으면 그 자체가 결함이다.

그런데 USB 기기가 잠드는 것은 위험하다. 자는 동안 들어온 바이트는 그냥 사라진다.
그래서 **자도 되는 조건**과 **얼마나 자도 되는가**를 따로 판단한다.

| 상태 | 하는 일 |
|---|---|
| 폰이 듣고 있음 (DTR ↑) | **자지 않는다.** 대신 할 일이 없으면 CPU 를 240MHz → 80MHz 로 스스로 내린다. 느려지는 것이지 자는 게 아니라 USB CDC 는 그대로 살아 있다 |
| 폰이 안 듣고 있음 + 3초간 조용 | light sleep. 버튼 눌림(GPIO 로우 레벨)과 타이머로 깨어난다 |
| 버튼이 눌린 채 / 전할 것이 남음 | 자지 않는다. 눌린 채로 자면 레벨 깨움이 즉시 걸려 오히려 전력을 더 쓴다 |

**깰수록 길게 잔다.** 처음엔 0.5초, 다음엔 1초, 그다음부터 2초.

```
  방금 쓰다 만 상황   ├─0.5s─┤├─1.0s─┤├──2.0s──┤├──2.0s──┤ …
                      ↑ 촘촘히 확인            ↑ 드물게 확인
```

밤새 안 쓰는 동안에도 0.5초마다 깨면 **그 깨어남 자체가 전력**이다. 그렇다고 무작정
길게 자면 앱이 다시 붙은 것을 늦게 알아차린다. 사람이 기기를 다시 쓰는 순간은
버튼 눌림으로 즉시 잡히므로, 길어진 슬라이스가 늦추는 것은 "앱이 혼자 다시 붙는 경우"뿐이다.

**슬라이스 상한을 규칙이 스스로 강제한다.** 자는 동안에는 어느 태스크도 워치독을
먹이지 못한다. 슬라이스가 워치독 시간을 넘으면 멀쩡한 기기가 "멈췄다"고 판정되어
재시작하는데, 겉으로는 "가끔 안 눌린다"로만 보여서 원인을 찾기가 아주 어렵다.
그래서 `clampSlice()` 가 어떤 설정값을 받아도 **워치독의 절반**으로 자른다.
상수를 잘못 고쳐도 이 사고는 나지 않는다 (`test_power_slice_never_outlasts_the_watchdog`).

**전류계 없이 절전을 확인하는 법.** 기기가 스스로 "켜져 있던 시간 중 얼마를
잠들어 있었는지"를 재서 `STATS2` 로 보고한다. 앱의 자가진단 화면 `절전` 항목에
`켜져 있는 동안 78.4% 를 잠들어 보냈어요 (절전 1,204회)` 처럼 나온다.

> 이 값은 **전류가 아니라 시간의 비율**이다. 소비 전류를 추정하지 않는다 —
> 실제 mA 는 아래 7-3 의 HIL 표에서 전류계로 재야 하고, 아직 재지 않았다.

## 6. 프로토콜 명세 (VKP v1)

### 6-1. 프레임 형식

```
 0xAA │ SEQ │ TYPE │ LEN │ PAYLOAD[LEN] │ CRC16_L │ CRC16_H │ 0x55
  (1)   (1)   (1)    (1)     (0~16)         (1)       (1)      (1)
```

| 항목 | 설명 |
|---|---|
| `STX` 0xAA | 시작 |
| `SEQ` | 1~255 순환. **0은 "답을 기다리지 않는 알림"** |
| `TYPE` | 아래 표 |
| `LEN` | payload 길이 (0~16). 범위를 벗어나면 즉시 버리고 재동기화 |
| `CRC16` | CRC-16/CCITT-FALSE (0x1021, init 0xFFFF), **SEQ부터 PAYLOAD 끝까지** 위에서 계산, 리틀엔디언 |
| `ETX` 0x55 | 끝. CRC를 통과해도 여기가 어긋나면 버립니다 |

### 6-2. 종류

**기기 → 폰**

| TYPE | 이름 | payload |
|---|---|---|
| 0x01 | `EVT_PRESS` | `button(1) kind(1) latencyUs(2, LE)` |
| 0x02 | `HELLO` | `proto(1) fwMajor(1) fwMinor(1) buttons(1) caps(1) resetReason(1)` |
| 0x03 | `STATS` | `sent(2) retx(2) ackTimeout(2) crcErr(2) uptimeSec(2) freeHeapKB(2) minHeapKB(2) edgeDrops(2)` — 모두 LE, 16바이트(규격 최대치) |
| 0x04 | `MAP` | `slot(1) index(1) count(1) data(0~13)` — 기기에 저장된 버튼 매핑 (조각 단위) |
| 0x05 | `STATS2` | `blocked(2) multi(2) stuck(2) burst(2)` — 주머니 오작동으로 걸러 낸 집계. STATS 의 payload 가 이미 16바이트라 종류를 나눴습니다 |

`kind` : 0 = 짧게, 1 = 길게(AI 도우미), 2 = 두 번

> `0x11` 은 예전에 진동 지시(FEEDBACK)로 쓰려던 번호입니다. 기기에 표시 장치가 없어
> 쓰지 않지만, 나중에 붙일 때를 위해 비워 두었습니다.

**폰 → 기기**

| TYPE | 이름 | payload | 뜻 |
|---|---|---|---|
| 0x10 | `ACK` | `ackSeq(1)` | "받았다" — 재전송 중단 |
| 0x12 | `PING` | 없음 | 기기가 `HELLO` + `STATS` + `STATS2` 로 답함 |
| 0x13 | `SET_MAP` | `slot(1) index(1) count(1) data(0~13)` | 이 버튼 매핑을 기기에 저장해 둬 |
| 0x14 | `GET_MAP` | 없음 | 기기가 저장해 둔 매핑을 `MAP` 으로 답함 |

### 6-3. 주고받는 흐름

```
 기기                                     폰(안드로이드)
  │                                          │
  ├─ EVT_PRESS(seq=7, btn=1) ───────────────►│
  │                                          ├─ ACK(7) 즉시 회신
  │◄─────────────────────────── ACK(7) ──────┤   (앱 여는 데 걸리는 시간을 기다리지 않음)
  │                                          ├─ 1번 앱 실행
  │                                          └─ 결과를 음성·진동·화면으로 사용자에게
```

**ACK가 안 오면** 150ms 뒤 **같은 SEQ로** 다시 보냅니다(최대 3회).
폰은 같은 SEQ를 두 번 실행하지 않으므로 앱이 두 번 열리는 일은 없습니다.
세 번 다 실패하면 실패 횟수를 세어 두고, 앱이 `PING` 할 때 `STATS` 로 돌려줍니다.
자가진단 화면의 **기기 펌웨어** 항목에 `응답 못 받음 N회` 로 나옵니다.
→ *"왜 안 되는지"를 사용자가 스스로 확인할 수 있는 근거가 됩니다.*

## 7. 검증

### 7-0. 빌드 검증 (2026-08-22 확인)

보드 없이도 "플래시에 올릴 수 있는 코드인가"는 확인할 수 있습니다.
ESP32 Arduino 코어 **3.3.11** 로 두 가지 USB 설정 모두 빌드했고, **우리 코드에서 경고 0개**입니다.

| USB 설정 (FQBN 옵션) | 결과 | 플래시 | RAM(전역) |
|---|---|---|---|
| Hardware CDC and JTAG (기본) | ✅ 통과 | 297,013 B (8%) | 23,608 B (7%) |
| USB-OTG TinyUSB (`USBMode=default`) | ✅ 통과 | 약 330 KB (10%) | 약 54 KB (16%) |

> TinyUSB 쪽 숫자는 진동 기능을 걷어내기 전에 잰 값이라 대략치입니다.
> 기본 설정(Hardware CDC)은 걷어낸 뒤 다시 재서 확인한 값입니다.

기본 설정 기준으로 플래시는 8%, RAM은 7%만 씁니다. (주머니 차단·매핑 저장을 넣고 다시 잰 값입니다) 앞으로 절전·NVS·터치 게이팅을
붙일 여유가 충분합니다.

재현 방법 (아두이노 IDE에 번들된 arduino-cli 사용):

```bash
CLI="/Applications/Arduino IDE.app/Contents/Resources/app/lib/backend/resources/arduino-cli"
export ARDUINO_DIRECTORIES_DATA="$HOME/Library/Arduino15"

"$CLI" core install esp32:esp32@3.3.11 \
  --additional-urls https://espressif.github.io/arduino-esp32/package_esp32_index.json

"$CLI" compile --fqbn esp32:esp32:XIAO_ESP32S3 --warnings all firmware/vibekey_firmware
```

> `XIAO_ESP32S3` 보드는 **USB CDC On Boot 기본값이 Enabled** 라서 IDE에서 따로 건드릴 것이 없습니다.
> (`arduino-cli board details -b esp32:esp32:XIAO_ESP32S3` 로 확인)

### 7-1. 단위 테스트 (PC에서, 기기 없이)

`vkp_frame.h` 와 `press_fsm.h` 는 Arduino 헤더를 쓰지 않는 순수 C++ 이라

그중 핵심은 "깨진 프레임이 실행으로 새어 나가는가" 입니다. 프레임 **200만 개**에

| 손상 정도 | CRC8 (초기 설계) | CRC16 (현재) |
|---|---|---|
| 1~3비트 (전선 잡음 수준) | 0건 | **0건** |

값을 그대로 적습니다. CRC8이 부실한 것도 아닙니다 — 여러 비트가 한꺼번에 망가질 때만
갈립니다. 그래도 올린 이유는 이 기기가 **화면 확인 없이** 동작하기 때문입니다.
새어 나간 한 건을 사용자가 알아챌 방법이 없습니다. 치른 비용은 프레임당 1바이트입니다.
→ *숫자를 보고 설계를 바꾼 기록입니다.*

## 8. 빌드 · 업로드

### 8-1. 아두이노 IDE 설정

| 항목 | 값 |
|---|---|
| 보드 | **XIAO_ESP32S3** (Seeed Studio XIAO ESP32S3) |
| USB CDC On Boot | **Enabled** ← 이걸 켜야 `Serial`이 네이티브 USB로 나갑니다 |
| USB Mode | USB-OTG (TinyUSB) 또는 Hardware CDC and JTAG |
| Upload Mode | USB-OTG CDC |
| 추가 라이브러리 | **없음** (ESP32 Arduino 코어만 있으면 빌드됩니다) |

코어 API를 특별히 가려 쓰지 않아서 **2.x / 3.x 양쪽에서 빌드**될 것으로 보이지만,
**실제로 확인한 것은 3.3.11 뿐입니다** (위 7-0).

### 8-2. 업로드가 안 될 때

부트 모드로 넣습니다: `BOOT` 버튼을 누른 채 `RESET`을 한 번 눌렀다 떼고, `BOOT`도 뗍니다.

### 8-3. 앱과 연결 확인

1. 케이블로 폰에 꽂으면 앱이 자동으로 뜨고 USB 권한을 묻습니다.
2. 앱 `설정 → 잘 되는지 검사하기 → 모두 검사하기` 의 **기기 펌웨어** 항목에
   `펌웨어 3.0 · 버튼 3개 · 프로토콜 v1` 이 뜨면 정상입니다.
3. 기기가 없어도 같은 화면의 `1번 / 2번 / 3번` 단추로 **진짜와 똑같은 프레임**을 넣어 시험할 수 있고,
   `깨진 신호 넣어 보기` 를 누르면 **아무 일도 일어나지 않는 것**을 확인할 수 있습니다.
