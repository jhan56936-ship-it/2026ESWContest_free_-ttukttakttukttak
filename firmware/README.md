# 바이브키 기기 펌웨어 (VibeKey Firmware 3.0)

Seeed Studio **XIAO ESP32-S3** 용 아두이노 스케치입니다.
버튼을 읽어 폰으로 보내고, 폰의 대답을 받아 **진동으로 되돌려 주는** 것까지가 이 펌웨어의 일입니다.

```
firmware/
├── vibekey_firmware/
│   ├── vibekey_firmware.ino   태스크 구성 · 핀 설정 · ISR (스케치 본체)
│   ├── vkp_frame.h            프레임 프로토콜(CRC16·재동기화)  ← 순수 C++, PC에서 테스트됨
│   ├── press_fsm.h            누름 판정 상태머신(디바운스·길게·떨림 가드) ← 순수 C++
│   └── haptics.h              진동 패턴 표 + LEDC PWM
├── test/
│   ├── test_vkp.cpp           단위 테스트 (PC에서 실행)
│   └── run_tests.sh
└── README.md                  ← 이 문서
```

---

## 1. 왜 펌웨어를 다시 썼는가

2.0까지 기기가 하는 일은 **GPIO를 읽어 `"True\n"` 을 뱉는 것**뿐이었습니다.
신호 해석, 손 떨림 방지(3초 디바운스), 실행 판단이 전부 안드로이드 쪽에 있었고,
기기는 사실상 전선이었습니다. 그래서 아래 세 가지 질문에 답할 수 없었습니다.

| 질문 | 2.0의 답 | 3.0의 답 |
|---|---|---|
| 화면을 안 보고 쓰는데, **눌린 걸 어떻게 압니까?** | 알 수 없음 | 버튼마다 다른 진동 (`haptics.h`) |
| **됐는지 안 됐는지**는 어떻게 압니까? | 알 수 없음 | 폰이 결과를 돌려주고 기기가 성공/실패 진동 |
| 잡음 한 번에 택시가 불리면? **신호 무결성은 누가 보장합니까?** | 아무도 | CRC16 + SEQ + ACK + 재전송 (`vkp_frame.h`) |
| 폰이 바쁘면 떨림 방지는? | 같이 무너짐 | 기기 상태머신이 독립적으로 판단 (`press_fsm.h`) |

한 줄로: **MCU를 '전선'에서 '시스템의 신뢰 코어'로 올렸습니다.**

2.0 펌웨어 원본은 [`legacy/sketch_jul10a_v2.ino`](legacy/) 에 그대로 남겨 두었습니다(40줄).
무엇이 왜 달라졌는지 줄 단위로 비교할 수 있습니다.

## 2. 핀맵

XIAO ESP32-S3 의 D 표기와 실제 GPIO 번호입니다.

| 기능 | 보드 표기 | GPIO | 모드 | 비고 |
|---|---|---|---|---|
| 1번 버튼 | D0 | 1 | `INPUT_PULLUP` | 눌리면 GND로 떨어짐 (LOW = 눌림) |
| 2번 버튼 | D1 | 2 | `INPUT_PULLUP` | |
| 3번 버튼 | D2 | 3 | `INPUT_PULLUP` | ⚠️ 부팅 스트래핑 핀 — 아래 참고 |
| 진동 모터 | D3 | 4 | `LEDC PWM` 20kHz / 8bit | MOSFET 게이트 |
| 지연 관측 | D10 | 9 | `OUTPUT` | 로직 애널라이저용 (`VK_LATENCY_PROBE`) |
| USB | — | 19/20 | 네이티브 USB CDC | 폰과의 통신 · 전원 |

**버튼 핀은 2.0 그대로입니다.** `firmware/legacy/sketch_jul10a_v2.ino` 가 쓰던 D0·D1·D2를
유지했기 때문에, 이미 만들어 둔 기기는 **다시 납땜하지 않고 펌웨어만 올리면** 됩니다.
새로 추가된 배선은 진동 모터(D3) 하나뿐입니다.

**핀 선택에서 주의한 것**

- `D2`(GPIO3) — 부팅 스트래핑 핀(JTAG 소스 선택)입니다. 전원이 들어오는 순간 3번 버튼이
  눌려 있으면 스트래핑 값이 바뀝니다. 정상 부팅에는 영향이 없어 기존 배선을 유지했지만,
  **기판을 새로 뜬다면 `D8`(GPIO7)로 옮기는 편이 안전합니다.**
  `vibekey_firmware.ino` 의 `BUTTON_PINS` 배열에서 `3` 을 `7` 로 바꾸기만 하면 됩니다.
- `D6`(GPIO43) / `D7`(GPIO44) — UART0 TX/RX라서 쓰지 않았습니다.
- `D4`(GPIO5) / `D5`(GPIO6) — I²C 기본 핀. 확장(센서 추가)을 위해 비워 두었습니다.

## 3. 회로

### 3-1. 버튼 (3개 동일)

내부 풀업을 쓰므로 외부 저항이 필요 없습니다. 스위치 양단의 100nF는 접점 튐을
전기적으로 한 번 걸러 주는 용도이고, 나머지는 펌웨어 디바운스(25ms)가 처리합니다.

```
   3V3
    │
    ⌇  (ESP32-S3 내부 풀업 ~45kΩ)
    │
    ├──────────────► GPIO 1 / 2 / 3   (D0 / D1 / D2)
    │
   ─┴─  택트 스위치
    │        ┌──┤├──┐  100nF (선택)
   GND ──────┴──────┘
```

### 3-2. 진동 모터

모터는 GPIO가 직접 못 켭니다(전류 부족 + 역기전력). N채널 MOSFET으로 로우사이드
스위칭하고, 코일의 역기전력을 다이오드로 흘려 보냅니다.

```
        3V3 ────────────┬───────────────┐
                        │               │
                     ┌──┴──┐        ▼ 1N4148
                     │모터 │        │  플라이백 다이오드
                     │(코인)│        │  (모터와 병렬, 역방향)
                     └──┬──┘        │
                        ├───────────┘
                        │
                     ┌──┴──┐ D
      GPIO 4 ──[1kΩ]─┤G AO3400 (N-ch MOSFET)
        (D3, PWM     └──┬──┘ S
         20kHz)         │
                        │
              [100kΩ]───┤   (게이트 풀다운 — 부팅 중 모터가 제멋대로 안 돌게)
                        │
                       GND
```

- **PWM 20kHz** — 가청 범위 위라서 모터가 "삐-" 하고 울지 않습니다. 세기는 duty로 조절합니다.
- **게이트 풀다운 100kΩ** — 부팅 직후 GPIO가 뜬 상태일 때 모터가 갑자기 도는 것을 막습니다.

## 5. 소프트웨어 구성

### 5-1. 태스크

Wi-Fi를 쓰지 않으므로 모두 core 1에 올렸습니다(core 0은 USB·시스템).

| 태스크 | 우선순위 | 주기 | 스택 | 하는 일 |
|---|---|---|---|---|
| `inputTask` | 4 | 10ms | 3072B | ISR 큐를 비우고 누름 종류 확정 (`press_fsm.h`) |
| `protoTask` | 3 | 5ms | 4096B | 프레임 송신 · ACK 대기 · 재전송 · 수신 해석 |
| `hapticTask` | 2 | 이벤트 | 2048B | 진동 패턴 재생 (LEDC) |
| `loopTask` | 1 | 1s | (기본) | 잠들어 있음 — 실제 일은 위 셋이 합니다 |

**큐**

| 큐 | 깊이 | 항목 크기 | 생산자 → 소비자 |
|---|---|---|---|
| `edgeQueue` | 32 | 12B (`EdgeMsg`) | ISR → `inputTask` |
| `pressQueue` | 8 | 12B (`PressMsg`) | `inputTask` → `protoTask` |
| `hapticQueue` | 8 | 1B | 아무 태스크 → `hapticTask` |

**delay() 를 한 번도 쓰지 않습니다.** 진동이 0.5초 울리는 동안에도 버튼 입력과
프레임 송수신은 멈추지 않아야 하기 때문에, 대기는 전부 `vTaskDelay` 입니다.

### 5-2. 누름 판정 (`press_fsm.h`)

```
        [대기] ──접점 LOW──► [눌림]
           ▲                   │
           │                   ├── 700ms 경과 ──► LONG 확정 (손 떼기 전에)
           │                   │                     │
           └──── 접점 HIGH ◄───┘                     ▼
                    │                            [대기(가드)]
                    ├── 직전 실행 후 1.2초 안 ──► 버림 (손 떨림)
                    └── 그 밖 ──────────────► SHORT 확정
```

- **디바운스 25ms** — 접점 튐 제거
- **길게 700ms** — 떼기 전에 확정합니다. 뗄 때까지 기다리면 "언제 떼야 하지?"를 모르는 어르신에게는 반응이 없는 것처럼 느껴집니다.
- **떨림 가드 1.2초** — 2.0에서 안드로이드에 있던 3초 디바운스를 기기로 옮긴 것입니다. 중복 실행은 SEQ가 따로 막아 주므로 시간을 3초에서 1.2초로 줄여 반응을 빠르게 했습니다.
- **두 번 누름(DOUBLE)은 기본 꺼짐** — 켜면 "한 번 누름"을 확정하려고 매번 0.35초를 기다려야 해서 모든 실행이 그만큼 느려집니다. 기능 하나보다 즉각 반응이 중요하다고 판단했습니다. (`FsmConfig::doubleEnabled`)

## 6. 프로토콜 명세 (VKP v1)

### 6-1. 프레임 형식

```
 0xAA │ SEQ │ TYPE │ LEN │ PAYLOAD[LEN] │ CRC16_L │ CRC16_H │ 0x55
  (1)   (1)   (1)    (1)     (0~16)         (1)       (1)      (1)
```

| 항목 | 설명 |
|---|---|
| `STX` 0xAA | 시작 |
| `SEQ` | 1~255 순환. **0은 "답을 기다리지 않는 알림"** |
| `TYPE` | 아래 표 |
| `LEN` | payload 길이 (0~16). 범위를 벗어나면 즉시 버리고 재동기화 |
| `CRC16` | CRC-16/CCITT-FALSE (0x1021, init 0xFFFF), **SEQ부터 PAYLOAD 끝까지** 위에서 계산, 리틀엔디언 |
| `ETX` 0x55 | 끝. CRC를 통과해도 여기가 어긋나면 버립니다 |

### 6-2. 종류

**기기 → 폰**

| TYPE | 이름 | payload |
|---|---|---|
| 0x01 | `EVT_PRESS` | `button(1) kind(1) latencyUs(2, LE)` |
| 0x02 | `HELLO` | `proto(1) fwMajor(1) fwMinor(1) buttons(1) caps(1)` |
| 0x03 | `STATS` | `sent(2) retx(2) ackTimeout(2) crcErr(2) uptimeSec(2)` — 모두 LE |

`kind` : 0 = 짧게, 1 = 길게(AI 도우미), 2 = 두 번

**폰 → 기기**

| TYPE | 이름 | payload | 뜻 |
|---|---|---|---|
| 0x10 | `ACK` | `ackSeq(1)` | "받았다" — 재전송 중단 |
| 0x11 | `FEEDBACK` | `pattern(1)` | 실행 결과를 진동으로 (5=성공, 6=실패) |
| 0x12 | `PING` | 없음 | 기기가 `HELLO` + `STATS` 로 답함 |

### 6-3. 주고받는 흐름

```
 기기                                     폰(안드로이드)
  │                                          │
  ├─ EVT_PRESS(seq=7, btn=1) ───────────────►│
  │  (동시에 "눌렸어요" 진동)                  ├─ ACK(7) 즉시 회신
  │◄─────────────────────────── ACK(7) ──────┤   (앱 여는 데 걸리는 시간을 기다리지 않음)
  │                                          ├─ 1번 앱 실행 시도
  │◄──────────────── FEEDBACK(성공/실패) ─────┤
  ├─ (성공이면 "톡톡", 실패면 무거운 "웅웅웅")   │
```

**ACK가 안 오면** 150ms 뒤 **같은 SEQ로** 다시 보냅니다(최대 3회).
폰은 같은 SEQ를 두 번 실행하지 않으므로 앱이 두 번 열리는 일은 없습니다.
세 번 다 실패하면 기기가 **0.5초 긴 진동**으로 "지금 폰이 못 받고 있다"를 알립니다.
→ *"폰이 죽으면 케이스는 플라스틱 조각"이라는 반문에 대한 답입니다.*

### 6-4. 진동 패턴

| 번호 | 이름 | 촉감 | 언제 |
|---|---|---|---|
| 1 | `BTN1` | 톡 | 1번 버튼 |
| 2 | `BTN2` | 톡톡 | 2번 버튼 |
| 3 | `BTN3` | 우웅 | 3번 버튼 |
| 4 | `AI` | 톡-우웅 | 길게 누름 |
| 5 | `OK` | 산뜻한 두 번 | 앱이 열렸음 |
| 6 | `FAIL` | 무거운 세 번 | 못 열었음 (앱 없음 등) |
| 7 | `LINK` | 점점 세게 | 폰과 이어짐 |
| 8 | `LOST` | 길게 한 번 | 폰이 세 번 다 못 받음 |

버튼마다 촉감이 다르므로 **화면을 보지 않고도 몇 번 버튼이 눌렸는지** 알 수 있습니다.

## 7. 검증

### 7-1. 단위 테스트 (PC에서, 기기 없이)

```bash
cd firmware/test
./run_tests.sh
```

`vkp_frame.h` 와 `press_fsm.h` 는 Arduino 헤더를 쓰지 않는 순수 C++ 이라
PC에서 그대로 컴파일됩니다. **41개 검사, 전부 통과**.

그중 핵심은 "깨진 프레임이 실행으로 새어 나가는가" 입니다. 프레임 10만 개에
무작위 손상을 먹여 잰 결과입니다. (씨앗 고정 — 언제 돌려도 같은 숫자)

| 손상 정도 | CRC8 (초기 설계) | CRC16 (현재) |
|---|---|---|
| 1~3비트 (전선 잡음 수준) | 0건 | **0건** |
| 4~10비트 (커넥터 흔들림·전원 튐) | 8건 (0.008%) | **0건** |

CRC8이 부실한 게 아니라 여러 비트가 한꺼번에 망가질 때만 갈립니다. 그래도 올린
이유는 이 기기의 오작동이 곧 **요금**이기 때문입니다. 치른 비용은 프레임당 1바이트입니다.
→ *숫자를 보고 설계를 바꾼 기록입니다.*

| 보드 | **XIAO_ESP32S3** (Seeed Studio XIAO ESP32S3) |
| USB CDC On Boot | **Enabled** ← 이걸 켜야 `Serial`이 네이티브 USB로 나갑니다 |
| USB Mode | USB-OTG (TinyUSB) 또는 Hardware CDC and JTAG |
| Upload Mode | USB-OTG CDC |
| 추가 라이브러리 | **없음** (ESP32 Arduino 코어만 있으면 빌드됩니다) |

ESP32 Arduino 코어 **2.x / 3.x 양쪽에서 빌드**됩니다 (LEDC API 차이는 `haptics.h`에서 흡수).

### 8-2. 업로드가 안 될 때

부트 모드로 넣습니다: `BOOT` 버튼을 누른 채 `RESET`을 한 번 눌렀다 떼고, `BOOT`도 뗍니다.

### 8-3. 앱과 연결 확인

1. 케이블로 폰에 꽂으면 앱이 자동으로 뜨고 USB 권한을 묻습니다.
2. 연결되면 기기가 **점점 세지는 진동**(LINK)을 한 번 냅니다.
3. 앱 `설정 → 잘 되는지 검사하기 → 모두 검사하기` 의 **기기 펌웨어** 항목에
   `펌웨어 3.0 · 버튼 3개 · 프로토콜 v1` 이 뜨면 정상입니다.
4. 기기가 없어도 같은 화면의 `1번 / 2번 / 3번` 단추로 **진짜와 똑같은 프레임**을 넣어 시험할 수 있고,
   `깨진 신호 넣어 보기` 를 누르면 **아무 일도 일어나지 않는 것**을 확인할 수 있습니다.
